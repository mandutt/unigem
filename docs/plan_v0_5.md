## 0. Hermes 작업 규칙 (먼저 읽을 것)

1. **실측 우선.** 이 문서의 가설(§6.2)은 사실이 아니다. 측정 로그 없이 "된다/안 된다"를 결론으로 쓰지 않는다.
2. **게이트는 사전등록되어 있다(§10).** 결과를 본 뒤 임계값을 바꾸지 않는다. 바꿔야 하면 사유를 기록하고 사용자 승인을 받는다.
3. **기존 운영 자산은 읽기 전용이다.** 언어 판정 파이프라인, 메모리 코어·DB, Hermes 코어는 수정하지 않는다. 신규 코드와 산출물은 신규 작업 디렉터리(`eg2-lab/`)에만 둔다. 기존 경로의 교체는 사용자 승인 후에만 한다.
4. **목표 하드웨어는 로컬 PC다.** Windows 11, CPU 전용, ONNX Runtime CPU EP, GPU 사용 금지. **지연·RAM·RTF 등 성능 게이트의 판정값은 로컬 PC 측정만 인정한다.** VPS 측정값은 "참고(VPS)"로 표시하고 게이트 판정에 쓰지 않는다 (§8.2).
5. **hang / OOM / 타임아웃은 1회 원인을 기록하고 중단 후 보고한다.** 우회·재시도·모델 교체는 사용자 지시 후에 한다. 로컬과 VPS 모두 모든 장시간 작업에 타임아웃과 메모리 상한을 건다.
6. **데이터는 공개 데이터 우선이다.** 각 작업의 데이터는 (1) 공개 데이터셋 조사·활용 → (2) 격차 분석 → (3) 격차분에 한해 외부 LLM API 합성 순으로 확보한다. 외부 LLM API는 학습 데이터 생성에만 허용하며, 호출 전에 §10의 G-DATA 승인을 받는다. **운영 추론 경로에서는 외부 LLM 호출을 하지 않는다.**
7. **데이터 등급 규칙 (VPS·외부 API 반출 통제).**
   - **P0 (공개·합성):** 공개 데이터셋, 규칙 기반 합성 데이터, 개인정보가 없는 합성 데이터. VPS 처리와 외부 LLM API 입력이 허용된다.
   - **P1 (개인):** 메모리 저장소 내용, 사용자 미디어·오디오, 사용자 화면 캡처, 사용자의 실제 입력 오타 등. **로컬 PC 밖 반출 금지.** VPS 전송 금지, 외부 LLM API 전송 금지. 보고서에는 원문 대신 해시·길이·통계만 쓴다.
   - 모든 작업(job)에 `data_class`를 명시하고, P1 작업은 VPS에 배정하지 않는다.
8. **가중치 정책.** 원본 체크포인트 파일은 **불변**이다(SHA256 기록·검증). 허용되는 것은 원본을 건드리지 않는 파생물이다: 헤드·어댑터·LoRA·prefix/프롬프트 튜닝 가중치, 어휘 pruning 사본, 양자화 사본, export된 ONNX. 금지되는 것은 원본 가중치를 직접 갱신하는 풀 파인튜닝과 EG2 상위 층 파인튜닝(참고 사례 QUAN 방식)이다. 필요해지면 별도 승인을 요청한다.
9. **시크릿 하드코딩 금지.** API 키·SSH 키·토큰은 환경변수 또는 자격증명 저장소로만 다루고, 코드·설정 파일·보고서·로그·job manifest에 출력하지 않는다.
10. **체크포인트(CP)에서 멈춘다.** CP0(VPS 준비 후), CP1(Phase A 후), CP2(Phase B 후), CP3(Phase C 각 실험 후), CP4(통합 전)에서 사용자 결정을 기다린다. 다음 Phase로 자동 진행하지 않는다.
11. **보고 형식.** 단계마다 `reports/<stage>.md`를 만든다(§14). 게이트는 **PASS / FAIL / INCONCLUSIVE**로 판정하고 FAIL·INCONCLUSIVE도 숨기지 않는다.
12. **모르는 것은 "모름"으로 보고한다.** 확인하지 못한 사실을 추정으로 채우지 않는다.

## 1. 프로젝트 목적

### 1.1 배경

EG2는 원래 메모리 시스템의 임베딩 모델로만 쓰일 예정이었다. 그러나 일반 PC(RAM 약 15.6GB, GPU 없음)에서는 용도별 특화 모델을 여러 개 상주시키기 어렵다. 이미 메모리 시스템의 일부로 항상 상주하는 EG2를 다용도로 활용할 수 있다면 모델 추가 없이 기능을 늘릴 수 있다.

EG2는 텍스트·코드·이미지·비디오·오디오를 하나의 768차원 공간으로 임베딩하는 멀티모달 모델이며, 텍스트 백본(hidden 512, 24층, 양방향)에 비전·오디오 타워가 soft token을 공급하는 구조다. Gemma 4 기반이다. 오디오 임베딩은 언어 판정에 **이미 Q8 ONNX로 운영 중**이다.

### 1.2 목표 기능

| # | 기능 | 방식(현재 가설) | 비고 |
|---|---|---|---|
| F1 | 오디오 언어 판정 | 프로토타입 + margin (기존 운영) | 회귀 방지 대상 |
| F2 | 한국어 STT (상주 경량 초벌 전사) | 동결 EG2 + CTC reader (기존 Notesoop-STT-Ko-v1 평가 우선) | komixv2(whisper 계열) 대체가 아님 |
| F3 | 비전 태깅 | 현재 화면 → 유사 이모지 검색 → 이모지 명칭을 태그화 | 디코더 사용 안 함 |
| F4 | 맞춤법 검사·교정 | 규칙 + (디코더 후보 재순위 또는 edit 태깅) | 정상 문장 보존 최우선 |
| F5 | 메모리용 중요정보 요약 | 디코더 생성 + 슬롯 보존 검증기 | 원문 불변, 요약은 파생 필드 |
| F6 | STT 후처리 | CTC 출력 → 디코더 교정·정규화 | F2와 디코더의 접점 |

### 1.3 설계 원칙

- **하나의 상주 인코더 + 작업별 경량 헤드.** 검색형 작업(F1, F3)은 검색 헤드, 정렬형 작업(F2)은 CTC 헤드, 텍스트 생성 작업(F4~F6)만 디코더를 쓴다.
- **디코더는 온디맨드.** 필요할 때 로드·언로드한다. 지연은 **몇 초 이내면 허용**, 빠를수록 좋다 (소프트 목표 §11). 상주 정책은 구현 후 결정한다.
- **모든 헤드는 폴백을 가진다.** 헤드 실패·저확신 시 기존 경로(whisper 계열 ASR, 규칙 기반, 원문 그대로 저장)로 떨어진다. 폴백은 1급 요구사항이다.
- **증거 기반 채택.** 새 경로는 기준선과 같은 데이터·같은 지표로 비교해 이길 때만 채택한다.
- **병렬화는 실험 속도를 위한 것이지 판정 기준이 아니다.** 분산 실행의 결과는 재현 가능해야 하고, 성능 판정은 목표 하드웨어에서만 한다.

### 1.4 비목표

- GPU 사용, 외부 GPU 서버 학습
- 원본 가중치를 갱신하는 풀 파인튜닝, 디코더 사전학습
- Q8 이외 추론 양자화(Q4 등)
- komixv2/whisper 계열 ASR의 즉시 대체
- 비전·영상 캡션의 자유 서술 생성
- 운영 추론 경로에서 외부 LLM API 호출

## 5. 확정 사실 (공개 자료, 확인일 2026-11-01)

Hermes는 구현 시 **실제 체크포인트·config에서 다시 확인**하고 revision을 기록한다.

### 5.1 EG2
- 출력은 L2 정규화된 768차원 벡터. Matryoshka 512/256/128 절단 지원(절단 후 재정규화 필요).
- 텍스트 타워: 양방향 24층, hidden 512, 컨텍스트 8192. 비전 타워(16층)·오디오 타워(12층)가 soft token을 텍스트 백본에 공급.
- 규모: 텍스트 270M / +비전 440M / +오디오 570M / 전체 740M. 비전·오디오 인코더는 필요할 때만 로드 가능.
- 오디오: 16kHz, 30초로 잘림, 초당 25 토큰. 비디오 최대 32프레임. 이미지 기본 토큰 예산 280.
- 텍스트 입력에는 짧은 태스크 접두사를 붙이고, 이미지·비디오·오디오에는 붙이지 않는다.
- 라이선스 Apache-2.0. 일부 공개 ONNX 배포본은 `sentence_embedding [B,768]`만 출력한다.

### 5.2 STT 선행 사례 (모두 자체 보고, 독립 검증 아님)
- **QUAN-Transcribe-1.0 (베트남어):** 오디오 인코더 상위 2/12층 파인튜닝 + 여러 층 출력 학습 가중합 + 6층 reader, CTC, 약 2,800h. 평균 WER 6.87%. *(상위 층 파인튜닝은 §0-8에 따라 이 프로젝트에서 금지)*
- **EmbeddingGemma-2-Transcribe-Reader (영어):** EG2 동결, 13.3M reader, 20만 단어 CTC, LibriSpeech 100h. test-clean 6.8%, test-other 15.1%. 입력은 오디오 soft token `[T,512]`(`embed_audio` 출력), 30초 윈도우 + 96토큰 겹침. 사례의 revision `914f7f89142e33e77833254d9c9b90c3cef7303b`, transformers 5.19.0, **기본 attention 사용(eager는 이 버전에서 오디오 마스크가 반전됨)**.
- **embeddinggemma2-turkish-stt (터키어):** EG2 동결, 8.3M 문자 CTC reader, FLEURS 8.3h. 오디오 토큰 위치의 hidden을 **4개 층(h0, h8, h16, last)** 연결해 입력. greedy WER 26.3% → LM + 철자 보정 15.5%. 5 epoch ablation에서 last+h16만 쓰면 dev WER 74.5%, 4개 층이면 59.2%.
- **Notesoop-STT-Ko-v1 (한국어, 확인 대상):** EG2 오디오 타워 + 경량 음향 리더(가중치 137MB, CTC) + 25,000 형태소·음절 어휘 + KenLM 3-gram 재점수(82.7MB). 학습 데이터는 AI Hub 한국어 강의 음성 약 300GB. 모델 카드 기준 Zeroth-Korean test(457문장) CER 16.21%, WER 45.40%, 강의 녹음 41분 field test CER 22.46%(같은 조건에서 Whisper-medium 26.68%, large-v3 25.55%), RTF 0.0251~0.0352. **측정 환경은 Apple M1 Pro(MPS, bf16)**이며 Linux CPU·Windows CPU 수치는 없다. 라이선스는 카드상 Apache-2.0. 입력 청크 16초 + 겹침 1초. **모두 자체 보고이며 비교 상대에 komixv2는 없고, field test는 녹음 1건이다.** 어떤 EG2 출력(오디오 타워 출력인지 백본 층인지)을 입력으로 쓰는지는 카드에 명시되지 않았고, 코드(`src/step2_extract_features.py`, `src/model.py`)로 확인해야 한다.
- 터키어 사례에서 pooled 어미 차이를 거의 구분하지 못했다. 한국어에도 유사한 한계가 있을 가능성이 있으나 **미검증**이다.

### 5.3 T5Gemma 2
- Gemma 3 기반 인코더-디코더. 270M-270M(총 약 370M, 비전 인코더 제외), 140개 이상 언어. 인코더·디코더 임베딩 공유(tied), 디코더 self/cross attention을 합친 **merged attention**.
- Gemma 4 최소 모델(E2B)은 BF16 기준 약 11.4GB 표기로 상주 디코더 후보에 부적합하다.

- Notesoop-STT-Ko-v1: 저장소 `LICENSE` 파일, **AI Hub 학습 데이터 약관이 파생 모델의 사용·재배포·미세조정에 미치는 영향**, 입력으로 쓰는 EG2 출력 지점과 특징 정규화, CPU/Linux에서의 실행 가능 여부, `kenlm` 설치 가능성(Linux, Windows)

| ID | 가설 | 검증 단계 |
|---|---|---|
| H1 | EG2 텍스트 마지막 층 hidden은 숫자·식별자·오타 같은 표면 정보를 많이 잃는다 | B1 |

| H4 | 두 토크나이저가 같아 토큰 1:1 정렬이 가능하다 | C0 |
| H5 | T5 계열 디코더는 동적 INT8에서 일부 연산에서 품질이 떨어진다 | C3·D2 |
| H6 | 한국어 CTC reader는 선행 사례처럼 소규모 데이터에서도 학습된다 | C2 |
| H7 | 이모지 검색은 화면 캡처에 충분히 적합한 태그를 준다 | C1 |

| H9 | VPS(공유 vCPU)에서의 상대적 arm 비교는 로컬 PC에서도 같은 순위를 보인다 | C3 (최종 후보는 로컬 재측정으로 확인) |
| H10 | Notesoop reader는 Q8 ONNX로 추출한 특징에서도 성능을 유지한다(PyTorch bf16 특징과의 분포 차이가 작다) | A3, C2-A3 |
| H11 | Notesoop의 자체 보고 CER이 독립 평가 세트와 CPU 환경에서도 재현된다 | C2-A1 |
| H12 | Notesoop reader를 komixv2 pseudo-label 또는 Q8 특징으로 미세조정하면 개선된다(라이선스 허용 시) | C2-B |

## 7. 공통 실측 프로토콜

1. **환경 스냅샷**(모든 보고서 첫머리): 호스트 ID(`local` 또는 `vps-N`), OS, CPU 모델·명령어 세트, RAM, Python, onnxruntime, torch, transformers, onnx, 주요 패키지 버전과 lock 해시, ORT 세션 옵션(스레드 수, 그래프 최적화 수준).
2. **입력 고정:** 평가 세트는 경로 + SHA256으로 기록하고 한 번 정한 뒤 바꾸지 않는다. 학습/검증/테스트를 분리하고 테스트는 최종 1회만 사용한다. **합성·pseudo-label 데이터와 평가 세트의 중복(누수)을 검사한다.**
3. **시드 고정.** 반복 측정은 중앙값과 범위를 함께 기록한다.
4. **지표 측정:** 지연(워밍업 후 N회, p50/p95), RAM(working set·private bytes의 peak), 로드 시간, CPU 사용률. VPS에서는 steal time도 기록한다.
5. **공정한 비교:** 같은 입력·정규화·지표·연산 예산. **서로 다른 호스트에서 측정한 지연·RAM·처리량을 직접 비교하지 않는다.** 같은 호스트 클래스 안에서만 상대 비교하고, 최종 후보는 로컬 PC에서 재측정한다.
6. **로그:** 원시 결과는 CSV/JSONL로 저장하고 보고서에는 요약표 + 로그 경로를 둔다.
7. **캐시 용량 사전 계산:** `프레임(또는 토큰) 수 × 차원 × 바이트`를 먼저 계산해 호스트의 디스크 여유와 비교한 뒤 추출한다.

## 8. 분산 실행 계획 (로컬 PC + VPS ×5)

### 8.1 자원 요약

| 자원 | 개수 | 사양 | 역할 |
|---|---|---|---|
| 로컬 PC | 1 | 6C/12T, 약 15.6GB | P1 데이터 처리, 최종 성능 판정, 통합, Windows 환경 검증 |
| VPS | 5 (`vps-1` ~ `vps-5`) | 4 vCPU, 8GB, 20GB | P0 데이터 병렬 실험, 데이터 수집·전처리, 재현·민감도 실험 |

### 8.2 분산 원칙

1. **P1은 로컬 전용, P0는 어디서나.** (§0-7) job manifest에 `data_class`가 없으면 실행하지 않는다.
2. **성능 판정은 로컬만.** VPS 수치는 "참고(VPS)". 같은 VPS 클래스 안의 상대 비교(arm A vs B)에는 사용 가능하나, 순위는 최종 후보를 로컬에서 재측정해 확인한다(H9).
3. **VPS 동일 클래스 활용.** 대조 실험의 arm은 가능하면 서로 다른 VPS에 같은 설정으로 배정해 동시에 실행한다(같은 하드웨어 조건 확보). 호스트 간 편차는 캘리브레이션(§8.6 V1)으로 보정·기록한다.
4. **1 VPS에 동시 1개 무거운 job.** vCPU 4개를 경합시키지 않는다. 스레드 수는 job별로 명시한다(기본 3~4, 시스템용 여유 확보).
5. **데이터는 작게, 결과는 더 작게.** 큰 캐시는 가능하면 생성한 VPS 안에서 소비하고, 로컬로는 체크포인트·지표·로그만 회수한다.
6. **재개 가능·멱등.** 모든 job은 체크포인트에서 재개할 수 있어야 하고 같은 manifest를 다시 실행해도 결과가 변하지 않아야 한다. VPS 재부팅·회수를 가정한다.
7. **가벼운 오케스트레이션.** SSH + rsync + manifest 기반 단순 러너만 쓴다. 클러스터 스케줄러·Ray 등 무거운 인프라를 도입하지 않는다. VPS에서 Docker는 쓰지 않는다(네이티브 venv).

### 8.4 VPS 디스크 예산 (20GB, 추정치 — 실측 `df`로 확인)

| 항목 | 목표 | 비고 |
|---|---|---|
| OS + 기본 패키지 | 약 3~5GB | 제공 이미지에 따라 다름 |
| 프로젝트 venv (CPU torch, transformers, onnxruntime 등) | 약 2~4GB | lock 파일로 고정, 필요한 패키지만 |
| 모델 파일 | 호스트별 필요한 것만 | EG2 FP32 체크포인트는 수 GB 가능, ONNX Q8 약 1GB 미만(추정). 디코더 후보도 각 1~2GB 수준 — **한 호스트에 모든 모델을 두지 않는다** |
| 작업 데이터·캐시 | **샤드당 약 5GB 이하** | STT 캐시: 4층 연결(2,304차원) × 25Hz × FP16 ≈ 시간당 약 0.4GB → 샤드당 약 12시간 이하가 이론 상한이나 여유를 두고 **5시간(약 2GB) 이하**로 시작 |
| 여유 | **항상 2GB 이상 유지** | 미달 시 job 시작 거부, 캐시 정리 |

모델·데이터는 작업이 끝나면 정리하고, 결과물만 회수한다.

### 8.5 job manifest 규격

각 작업은 `jobs/<job_id>.json`으로 기술한다 (시크릿은 포함하지 않는다).

```json
{
  "job_id": "C3-armA2-s1",
  "stage": "C3",
  "host": "vps-2",
  "data_class": "P0",
  "env_lock": "env/lock_linux_2026-11-01.txt",
  "inputs": [{"path": "data/c3/train.jsonl", "sha256": "..."}],
  "cmd": "python train/adapter_t5g2.py --config cfg/a2.yaml --seed 1",
  "resources": {"threads": 4, "mem_limit_gb": 6.5, "timeout_s": 28800},
  "outputs": [{"path": "runs/C3-armA2-s1/"}],
  "resume": true,
  "seed": 1
}
```

러너는 다음을 보장한다: `data_class` 검사(P1이면 VPS 거부), 디스크 여유 확인, 메모리 상한 적용(`ulimit`/`systemd-run` 등 가능한 수단), 타임아웃, 상태 기록(`queued/running/done/failed/oom/timeout`), 로그와 결과 JSONL 회수, 입력 해시 검증.

### 8.6 VPS 준비 단계 (Phase V)

#### V0. 호스트 점검
- 각 VPS의 배포판·커널·glibc·Python 버전, `lscpu` 결과, 명령어 세트(avx2/avx512/vnni 등), RAM, 디스크, 네트워크 대역(HF/외부·로컬 간 rsync), steal time을 기록한다. cgroup 기반 메모리 상한(`systemd-run` 등) 사용 가능 여부도 확인한다.
- 제공사 약관(장시간 CPU 사용, 트래픽 한도)을 확인해 보고한다.

#### V1. 환경 구성 및 캘리브레이션
- Python venv를 구성하고 lock 파일을 만들어 5대에 동일하게 설치한다.
- **정합 검증:** 같은 입력(공개 샘플)에 대해 로컬 PC와 각 VPS에서 동일 ONNX/torch 모델의 출력 cosine을 비교한다 (FP32 기준 ≥ 0.999 기대).
- **캘리브레이션 벤치:** 고정 입력의 ONNX 추론(FP32/INT8)과 소형 학습 스텝을 각 호스트에서 N회 측정해 호스트 간 상대 속도 계수를 기록한다.

#### V2. 러너와 안전장치
- manifest 러너, 자원 상한, 디스크 가드, 로그 회수, 정리 스크립트를 구성한다.
- 시크릿은 환경변수/자격증명 저장소로만 전달한다 (§0-9).

**G-V0 통과 기준:** 5대 모두 (a) venv 설치와 정합 검증 통과, (b) 자원 상한·디스크 가드 동작, (c) 캘리브레이션 결과 기록, (d) P1 반입 차단 확인.
**CP0:** 사용자에게 VPS 준비 결과와 역할 배정 확정을 보고한다.

### 8.7 재현성·정합 규칙
- 모든 호스트는 같은 모델 revision, lock 파일, 시드, 데이터 해시를 사용한다.
- 호스트가 다른 결과끼리는 수치 허용오차를 사전에 정한다(FP32 cosine ≥ 0.999, 학습 결과는 시드 반복 범위로 비교).
- Linux ONNX 결과와 Windows ONNX 결과가 어긋나면 **Windows(로컬) 결과를 기준**으로 하고 원인을 보고한다.

### 8.8 장애·보안·정리
- VPS는 재부팅·회수 가능성이 있으므로 체크포인트를 주기적으로 저장하고 로컬로 회수한다.
- 작업 종료 시 데이터·캐시·모델을 삭제하고 남은 용량을 기록한다. 외부 LLM API 호출 로그(모델, 횟수, 비용)는 호스트에 남기지 않고 로컬로 회수 후 삭제한다.
- SSH 접속은 키 기반으로 하고, 비밀번호·키를 로그에 남기지 않는다.

### Phase C — 헤드별 실험 (병렬)

#### C-D0. 공개 데이터 조사 (모든 C 단계의 선행, `vps-5`)
- 각 작업(C1 이미지, C2 한국어 음성, C4 맞춤법, C5 요약, C3 공통 텍스트)에 대해 **공개 데이터셋을 먼저 조사**하고 표로 보고한다: 이름, 규모, 언어, 라이선스, 접근 요건(신청 필요 여부), 작업 적합도, 확보 방법.
- **C2 후보(Hermes 확인):** Zeroth-Korean(Notesoop 평가에도 쓰인 세트), FLEURS ko, Common Voice ko, AI Hub 한국어 강의·일반 음성 등. AI Hub는 신청 절차와 이용 조건을 확인하고, 신청이 필요한 경우 사용자에게 요청 사항을 보고한다.
- 확보 가능한 공개 데이터를 우선 사용한다. 격차를 정량화한다(예: 한국어 맞춤법 오류 유형 중 공개 데이터가 커버하지 못하는 것, 메모리형 요약 쌍의 부족분).
- **격차가 남을 때만** 외부 LLM API 합성을 제안한다. 제안서에는 목적, 입력(P0임을 명시), 모델, 호출 수·토큰 추정, 예상 비용, 품질 검증 방법을 포함한다. **G-DATA 승인 전에는 호출하지 않는다.**
- **산출물:** `reports/C-D0_public_data_survey.md`, `reports/C-D0_llm_synthesis_proposal.md`(필요 시)

#### C0. 사전 타당성 점검 (`vps-1`)
- 토크나이저 비교: EG2와 T5Gemma 2의 `tokenizer.json` 해시, 어휘 일치율, 샘플 분할 일치율 (H4).
- T5Gemma 2의 외부 `encoder_outputs` 주입 생성 가능 여부와 decoder hidden size. 더미 hidden으로 `generate` 확인.
- 디코더 분리 시 필요한 텐서(임베딩/LM head/tied 설정/generation config)와 파라미터 수·파일 크기를 **텐서 단위로 직접 계산**(모델명의 270M을 디코더 크기로 쓰지 않는다). mT5-small도 동일.
- **산출물:** `reports/C0_feasibility.md`

#### C1. 비전 태깅: 이모지 검색 헤드 (F3, `vps-5`)
- **이모지 후보표:** Unicode CLDR 기준 이모지 + 영어/한국어 명칭·키워드. 스킨톤·성별 변형은 대표형으로 병합하고, 화면 태깅에 부적합한 그룹(국기 등)은 제외 옵션을 둔다. 화면 유형 보조 라벨(터미널, 코드 편집기, 브라우저, 문서, 채팅, 스프레드시트, 영상 재생 등)을 후보표에 추가한다.
- **후보 임베딩:** 후보 텍스트를 EG2 텍스트 접두사 규칙에 맞춰 임베딩해 사전 계산. 접두사·문구 형식(명칭만/명칭+키워드)과 다중 프롬프트 평균을 비교.
- **추론:** 이미지 임베딩과 후보의 cosine top-k, **margin 미달 시 태그 없음(reject)**. 프레임 변화 감지(해시 차이)가 있을 때만 이미지 임베딩을 계산한다.
- **평가 이미지(공개 데이터, P0):** 약 100장. 화면 캡처 유형(웹/모바일 UI, 코드·터미널, 문서 등) 약 70장 + 일반 사진 약 30장을 기본으로 하되 Hermes가 구성안을 제안한다. 공개 UI 스크린샷 데이터셋과 CC 라이선스 사진 데이터셋 후보를 C-D0에서 조사하고 라이선스를 확인한다. 사용자 화면 캡처는 필수가 아니며, 사용하려면 로컬 전용(P1)으로 별도 승인한다.
- **라벨링 프로토콜 (사용자 라벨 + VLM 보조, 앵커링 편향 방지):**
  1. 이미지마다 후보 풀을 만든다: (a) EG2 top-5 이모지, (b) 소형 VLM(예: Qwen3-VL 2B)에게 **같은 후보표 안에서** 이모지 최대 3개를 고르게 한 결과, (c) 무작위 방해 후보 약 3개.
  2. 후보를 합쳐 중복 제거 후 **섞고, 출처를 숨긴다.** 사용자는 각 후보를 적합/부분 적합/부적합으로 판정하고, 누락된 적절한 이모지를 직접 추가할 수 있다.
  3. VLM 출력은 후보 생성원일 뿐 **정답이 아니다.** 평가는 사용자 판정만 근거로 한다.
  4. 풀링 방식의 한계를 보고한다: 어느 출처에도 없는 이모지는 판정되지 않으므로 recall은 하한 추정이며, 주 지표는 판정된 후보 기준의 정밀도와 적합 태그 확보율이다.
  5. 라벨링 시트는 로컬에서 쓰는 CSV 또는 단일 HTML 파일로 생성한다. VLM 보조 라벨 도구는 오프라인 보조 도구라 ORT 제약 대상이 아니다(이미지는 P0). Qwen3-VL-2B는 로컬·VPS 모두 실행 가능함을 사용자가 확인했다. 실행 방식(런타임·정밀도), 모델 revision, 이미지당 처리 시간·RAM을 기록하고, 라이선스는 Hermes가 확인해 보고한다(§6.1).
- **측정:** top-1/top-3 적합률, margin 임계값별 reject율 대 부적절 태그율 곡선, VLM과 EG2의 후보 일치율(참고), 이미지 임베딩 지연(로컬, 텍스트+비전 구성), RAM 증가량.
- **산출물:** `reports/C1_emoji_tagging.md`, 후보표 파일, 라벨링 시트

#### C2. 한국어 STT (F2, `vps-3` + 로컬)

**순서: C2-A(기존 한국어 EG2 reader 평가) → 결과에 따라 C2-B(미세조정 또는 자체 학습).** 선행 사례 중 한국어는 Notesoop뿐이고 대규모 데이터(약 300GB)로 학습되어 있으므로, 처음부터 학습하기 전에 이것이 쓸 만한지를 먼저 측정한다.

##### C2-A. Notesoop-STT-Ko-v1 평가 (신규, 최우선)
- **C2-A0 코드·라이선스 점검(`vps-3`):** 저장소를 revision(커밋 해시) 고정으로 받아 `LICENSE`, README, `src/step2_extract_features.py`, `src/model.py`, `src/decoder.py`를 분석해 다음을 문서화한다: 입력 특징이 EG2의 어느 지점인지, 차원·프레임레이트·정규화, reader 구조·파라미터 수·출력 단위(CTC 여부), 디코딩 경로(greedy / KenLM 빔), 청크·겹침 병합 방식, MPS 전용 코드 경로 유무(CPU에서 `bfloat16` 동작 여부 포함). 샘플 오디오(`sample_audio.wav`)를 Linux CPU에서 재현해 모델 카드 결과와 일치하는지 본다. AI Hub 약관이 파생 모델 사용·미세조정에 영향을 주는지 확인해 보고한다.
- **C2-A1 독립 평가(`vps-3`, 공개 데이터 P0):** Zeroth-Korean test, FLEURS ko test에서 **komixv2, whisper-turbo(한국어 강제), Notesoop(greedy / +KenLM)**을 같은 정규화(구두점 제거, 띄어쓰기 영향을 분리해 CER 주지표)로 비교한다. CER·WER, RTF, RAM을 기록한다. VPS RTF는 참고, 판정용 RTF는 로컬 CPU에서 측정한다.
- **C2-A2 환경 평가(로컬, P1):** 사용자가 검수한 소규모 holdout(§C2-3의 표본)과 긴 녹음(청크 경계, 잡음, 겹침 병합)에서 CER과 이상 동작(반복, 누락, 환각)을 비교한다. 결과는 통계만 보고한다.
- **C2-A3 호환성(G-C2a, 제안):** 우리 ONNX(FP32·Q8)로 추출한 특징을 Notesoop reader에 넣었을 때의 CER을 원 PyTorch 특징 경로와 비교한다. 악화가 크면 (i) FP32 ONNX 사용, (ii) reader를 Q8 특징으로 미세조정(라이선스 허용 시), (iii) STT 경로만 PyTorch로 유지(RAM 비용) 중에서 사용자와 선택한다.
- **C2-A4 CPU 이식:** reader(137MB)의 ONNX export 가능성, KenLM의 Linux·Windows 설치 가능성(Windows 빌드 이슈 가능), 로컬 CPU에서 RTF·RAM을 측정한다. kenlm이 Windows에서 막히면 대체 재점수 방식을 보고한다.
- **판단(CP3):** 다음 중 선택을 사용자와 결정한다. 채택은 G-C2의 CER 기준(FLEURS ko test greedy CER ≤ 15%)을 후보에도 동일하게 적용한다. 모델 카드의 Zeroth CER 16.21%는 이 기준보다 높은 값이므로 **통과를 가정하지 말고 실측한다**(Zeroth와 FLEURS는 세트가 다르다).
  1. 그대로 채택 · 2. 채택 + 미세조정(C2-B의 일부) · 3. 자체 reader 학습(C2-B 전체) · 4. 폐기

##### C2-B. 자체 reader 학습 / 미세조정 (C2-A 결과에 따라 범위 결정)
- 시작점: Notesoop reader 가중치가 라이선스상 사용 가능하면 그 가중치에서 미세조정(원본 EG2는 동결 유지), 아니면 터키어 사례 구조로 처음부터. 아래 단계는 처음부터 학습하는 경우의 절차이며, 미세조정이면 C2-2와 C2-3의 데이터·평가를 같은 방식으로 적용한다.
- **C2-0 사전 점검(`vps-3`, 공개 데이터):** 한국어 오디오 임베딩이 대응 텍스트와 검색으로 맞는지(오디오→텍스트 R@1/R@10) FLEURS ko로 확인. sanity check이며 STT 성능을 보장하지 않는다.
- **C2-1 특징 추출 캐시:** 선택 층의 오디오 토큰 hidden(25Hz)을 FP16으로 캐시. 호스트 디스크 기준 샤드(≤ 약 5h)로 나눠 추출하고(§8.4), 30초 윈도우 + 겹침으로 긴 오디오를 처리한다.
- **C2-2 reader 학습:** 동결 EG2 위 소형 reader를 CTC로 학습. 시작 구조는 터키어 사례를 따른다(층 연결 → LayerNorm → Linear → 소형 transformer 4층 → 출력). **업샘플링 유무**, **출력 단위(자모 / 상위 N 음절 / 토큰)**, **층 조합(last+1층 vs 4개 층)**을 smoke test 규모로 비교(VPS 병렬 스윕). 증강(SpecAugment류)과 과적합을 관리한다.
- **C2-3 학습 데이터:**
  - **공개 한국어 음성(P0, 우선):** FLEURS ko, Common Voice ko 등. 가용성·라이선스·접근 요건은 C-D0에서 확인.
  - **pseudo-label(P1, 로컬 전용, 보조):** 사용자 미디어에서 komixv2 전사를 정답으로 사용할 수 있으나, **komixv2는 한국어 전용 파인튜닝 모델**이므로 대상 오디오를 엄격히 선별한다.
    - 기존 EG2 언어 판정에서 **모든 VAD 크롭이 한국어(margin 기준 충족)**인 클립만 채택. 한 크롭이라도 다른 언어로 판정되면 클립 전체 제외(혼합·코드스위칭 배제).
    - 음악·소음·비음성 구간 제외(VAD 음성 비율 하한), 길이 약 3~30초.
    - komixv2 디코딩 진단(평균 log-prob, no-speech 확률, 압축비 등)으로 환각·저신뢰 전사 제외.
    - 가능하면 보조 ASR(whisper-turbo, 한국어 강제)과의 일치도(CER 임계값 이하)로 이중 필터.
    - 소스·화자·길이 다양성 확보를 위해 소스별 상한을 둔다.
    - 선별 결과의 라벨 오류율을 사용자가 표본(약 50~100클립)으로 검수하고, 오류율을 보고한다.
    - pseudo-label 데이터는 학습에만 쓰고 **평가에는 절대 쓰지 않는다.** 이 특징 추출·학습은 로컬에서 수행한다(최종 reader 학습도 로컬).
- **평가:** **CER 필수**(한국어는 띄어쓰기 영향으로 WER 단독 사용 금지), WER 병기. 사람 라벨이 있는 공개 holdout(FLEURS ko test 등)과 사용자가 검수한 소규모 holdout에서 **komixv2·whisper-turbo·Notesoop-STT-Ko-v1과 같은 세트로 비교**. RTF, RAM, 로드 시간은 로컬에서 측정한다.
- **산출물:** `reports/C2_ko_ctc.md`, 선별 필터 보고서, 학습 로그, reader 체크포인트

#### C3. 텍스트 디코더 비교 (F4·F5·F6의 생성부)
같은 데이터·같은 학습 예산·같은 평가로 아래 arm을 비교한다. 데이터는 C4·C5의 공통 소규모 세트(수백 샘플, P0)를 쓴다.

| Arm | 구성 | 학습 | 배정 호스트(초안) |
|---|---|---|---|
| A0 | 규칙/추출형(비신경) | 없음 | 로컬 또는 임의 |
| A1 | T5Gemma 2 네이티브 인코더 + 디코더 | LoRA(attention 위주) | `vps-1` |
| A2 | EG2 다층 hidden → 어댑터 → T5Gemma 2 디코더 | 어댑터(+ 선택적 LoRA), 원본 동결 | `vps-2` |
| A3 | EG2 hidden → 어댑터 → mT5-small 디코더 | 어댑터(+ 선택적 LoRA) | `vps-4` |
| A4 (선택) | A2 + 어댑터 사전학습(feature matching) | 어댑터 → 작업 SFT | C0에서 토크나이저 정렬이 확인될 때만 |

- **동일 호스트 클래스 비교:** arm A1~A3는 서로 다른 VPS에서 같은 설정·같은 시드로 동시에 학습한다. 호스트 편차는 §8.6 V1 계수로 보정해 기록한다(H9).
- **허용 수단(§0-8):** LoRA, 어댑터, prefix/프롬프트 튜닝, 어휘 pruning 사본. 원본 풀 파인튜닝은 금지.
- **어휘 pruning:** 한·영·일·중에서 실제 쓰는 토큰만 남긴 **사본**을 만들어 파일 크기·RAM·학습 시 softmax 비용을 줄이고 품질 변화를 측정한다.
- **KV cache:** merged attention 구조에서는 메모리 K/V를 매 스텝 재계산하면 느리다. 메모리 K/V를 1회만 계산하는 그래프 분리와 decoder-with-past export 가능성을 확인한다.
- **어댑터 초기화:** identity 초기화는 공간이 다르면 의미가 없다. A4가 불가하면 소량 데이터로 바로 SFT하되 불안정(NaN, 발산)을 기록한다.
- **Q8 점검:** 선택된 arm에 대해 FP32 대비 Q8 품질 저하를 측정하고, 저하 시 특정 MatMul을 FP32로 남기는 옵션을 시험한다(H5).
- **최종 판정은 로컬 재측정:** VPS에서 상위로 뽑힌 후보(최대 2개)는 로컬 PC에서 학습 step 시간·추론 지연·RAM을 재측정하고, 순위가 유지되는지 확인한다.
- **채택 규칙:** A2가 A1 대비 핵심 지표 −2%p 이내이면서 상주 RAM 또는 지연에서 이득이 있을 때만 EG2 연결을 채택한다. 아니면 A1(네이티브 디코더, 온디맨드)로 간다.
- **산출물:** `reports/C3_decoder_arms.md`

#### C4. 맞춤법 검사·교정 (F4, `vps-4` + 로컬)
- **원칙:** 정상 문장을 건드리지 않는 것이 최우선. 확신이 낮으면 자동 수정하지 않고 후보로만 제시(reject option).
- **구성 비교:** (1) 규칙만 (2) 규칙 후보 + 디코더 로그우도 재순위 (3) EG2 토큰 hidden 위 edit 태깅 헤드(B1 통과 시) (4) 생성형 교정(비교용).
- **데이터(공개 우선):** 공개 한국어 교정·오류 코퍼스를 C-D0에서 조사해 우선 사용. 부족한 오류 유형은 규칙 기반 합성(자모 치환·탈락, 띄어쓰기 삭제/삽입, 조사·어미 혼동, 키보드 인접 오타)으로 보강하고, 그래도 부족하면 G-DATA 승인 후 LLM API 합성. **정상 문장을 절반 이상** 포함해 과교정을 측정한다. 사용자의 실제 입력 오타(P1)는 로컬 전용 소규모 평가용으로만 쓴다.
- **지표:** 오류 탐지 precision/recall, 교정 precision/recall, CER, **과교정률, 정상 문장 보존률**, 의미 보존(사람 표본 점검).
- **산출물:** `reports/C4_spellcheck.md`

#### C5. 메모리용 중요정보 요약 + 슬롯 검증기 (F5)
- **처리 원칙:** 저장 여부는 기존 판별기(JEV 등)가 정한다. 디코더는 선택된 내용의 정리·압축만 담당. **요약은 원문을 대체하지 않는 파생 필드**이며 원문은 불변이다.
- **슬롯 검증기(필수 게이트):** 원문에서 정규식으로 슬롯(숫자·금액, 날짜·시간, 버전, 파일명·경로, 영문 식별자·모델명, URL)을 추출해 (1) 요약에 모두 있는지 (2) 원문에 없는 슬롯이 새로 생기지 않았는지 검사. 위반 시 **요약 거부 → 원문 그대로 저장**.
- **데이터(공개 우선):** 공개 대화·문서 요약 데이터셋과 정보 추출형 데이터를 C-D0에서 조사해 우선 활용. 메모리형 요약(선호·환경·제약·결정 중심)의 격차는 **개인정보가 없는 합성 입력**으로 LLM API 합성(G-DATA 승인 후). **기존 메모리 저장소의 (원문, 저장문) 쌍은 P1**이므로 VPS·외부 API로 보내지 않고, 로컬에서만 평가 또는 소규모 학습 보조로 쓴다. 사용 가능 여부는 먼저 읽기 전용으로 확인한다.
- **구성 비교:** A0(추출형·템플릿) vs C3에서 선택된 디코더 arm.
- **지표:** 슬롯 보존율, 신규 슬롯 생성율(환각), 핵심 사실 보존(사람 표본 점검), 중복률, 압축률. ROUGE 단독 판정 금지.
- **산출물:** `reports/C5_summary.md`, 슬롯 검증기 코드

**CP3 (Phase C 각 실험 후):** 실험별로 채택/보류/폐기를 사용자와 결정한다.

### Phase D — 통합 (CP3에서 채택된 항목만, **로컬 PC 전용**, VPS는 회귀·장시간 테스트 보조)

#### D1. STT → 디코더 후처리 (F6)
- C2에서 채택된 STT 출력에 대해 후처리 방식을 비교한다: (a) greedy CTC, (b) KenLM 재점수(Notesoop 방식, 가능한 경우), (c) 디코더 교정(띄어쓰기·구두점·숫자 표기), (d) KenLM + 디코더 교정. CER/WER 변화, 지연 증가량, 과교정(발화에 없는 내용 추가)을 측정한다. komixv2 일치율은 보조 지표일 뿐 정답이 아니다.

#### D2. 디코더 ONNX Q8 배포
- 선택된 arm만 대상. 디코더(+ 어댑터 + 어휘 pruning)를 ONNX로 export, 동적 INT8 양자화, KV cache 구조 적용. FP32 대비 품질·크기·지연 비교, ORT CPU(Windows)에서 정상 생성 확인.

#### D3. 온디맨드 로더
- lazy load / idle timeout 언로드, 로드 지연, 동시 상주 시 RAM(EG2 + 헤드 + Hermes/JEV 일반 사용 프로세스)을 측정해 보고한다. **상주 정책은 이 측정값을 보고 사용자가 이후 결정한다.**

#### D4. 폴백·장애 처리
- 헤드 실패/타임아웃/저확신 시 폴백 동작 테스트(STT→기존 ASR 경로, 교정→규칙 결과 또는 원문, 요약→원문 저장). VPS는 반복 회귀·장시간 소크 테스트에 보조적으로 쓴다.
- 메모리 시스템과의 인터페이스(호출 방식·로그 필드)는 **사용자 승인 후 설계**한다. 기존 코어를 수정하지 않는 어댑터 형태로 제안한다.

**CP4 (통합 전):** 운영 반영 여부는 사용자 결정.

| G-C1 | C1 | top-1 적합 ≥ 70%, top-3 ≥ 85%, margin 통과 후 부적절 태그 ≤ 5% (약 100장, 사용자 판정 기준) | 도메인 갭이 크면 라벨 체계 재설계 | 이미지 임베딩 지연은 로컬 |
| G-C2 | C2 | 자체 학습은 smoke test에서 loss 수렴, **자체 학습·기존 reader 채택 모두** FLEURS ko test greedy CER ≤ 15% (PoC) | 불수렴 또는 CER이 15%를 크게 초과 | CER은 어디서나, RTF·RAM은 로컬 |
| G-C2a *(제안, 승인 필요)* | Notesoop 호환성 | Q8 ONNX 특징 사용 시 원 PyTorch 특징 대비 CER 상대 증가 ≤ 10% | 초과 시 §C2-A3의 (i)~(iii) 중 사용자 결정 | 로컬 |
| G-C3 | C3 | §C3 채택 규칙 | A2가 A1에 크게 열세이면 EG2 연결 폐기 | 후보 재측정은 로컬 |
| G-C4 | C4 | 정상 문장 보존률 ≥ 99.5%, 과교정률 ≤ 0.5%, 교정 precision 우선 | 정상 문장을 빈번히 변경 | VPS 가능 |
| G-C5 | C5 | 슬롯 보존율 ≥ 99%, 신규 슬롯 생성율 ≤ 1% (검증기 통과분 기준 0) | 환각이 검증기로 통제 불가 | VPS 가능 |
| G-D | 통합 | **판정 없음.** RAM·지연·상주 비용을 측정해 보고 | - | 로컬 |

**변경 사항(사용자 지시 반영):** G-D의 RAM·지연 상한(v0.3 초안)은 폐기하고 측정·보고 항목으로 전환했다. G-DATA와 G-V0는 신규 게이트다. 나머지 임계값은 v0.3 초안 그대로 사전등록한다. **G-A3S와 G-C2a는 v0.5에서 새로 제안한 것이며 사용자 승인 전에는 판정이 아니라 측정·보고로만 취급한다.**

## 11. 측정 항목 (판정 기준 아님, 보고용)

| 항목 | 소프트 목표 | 비고 |

## 13. 결정 기록

### 13.1 확정 (2026-11-01)
1. 지연: 즉시 수준은 불필요, 몇 초 이내면 허용, 빠를수록 좋음 → §11 소프트 목표
2. 학습 데이터: 외부 LLM API 허용, 공개 데이터 우선 → §0-6, G-DATA
3. 상주 RAM·정책: 구현 후 결정 → G-D 판정 없음
4. komixv2 pseudo-label 허용, 한국어 전용 모델이므로 대상 오디오 선별 필수 → C2-3
5. 비전 이미지: 공개 데이터 + 사용자 라벨 또는 VLM 후보 생성 후 사용자 검수 → C1 프로토콜
6. 원본 가중치를 건드리지 않는 수단 허용 → §0-8
7. 게이트 임계값 승인 → §10
8. 보조 자원: VPS 5대(4 vCPU/8GB/20GB) → §8
9. VPS 운영체제는 Linux → §3.2
10. Qwen3-VL-2B는 로컬·VPS 모두 실행 가능, 라이선스는 Hermes 확인 → C1, §6.1
11. 한국어 STT 참고 모델 Notesoop-STT-Ko-v1을 확인 대상으로 포함 → C2-A

### 13.2 남은 결정(해당 시점에 Hermes가 요청)
- CP0: VPS 역할 배정 확정, VPS 약관 확인 결과에 따른 조정
- C2-A 결과: 채택 / 채택 + 미세조정 / 자체 학습 / 폐기 선택, G-A3S·G-C2a 승인 여부
- G-DATA: LLM API 합성 제안서 승인(모델·호출 수·비용)
- C1: 평가 이미지 구성안(스크린샷/사진 비율, 데이터셋 선정) 승인, VLM 선정
- C2: pseudo-label 대상 미디어 범위와 라벨 검수 분량
- CP3·CP4: 채택/보류/폐기, 운영 반영

```text
8. 다음 단계 제안 (결정은 사용자)
```
